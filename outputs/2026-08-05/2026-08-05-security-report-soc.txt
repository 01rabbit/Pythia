1. デバイスコードフィッシング急増に対するEntra ID側の設定確認
観点: ゼロデイ関連
採用契機: γ / δ / ε
------------------------------------------------------------

優先度: 高
対象: Microsoft Entra ID / Microsoft 365

【24時間以内の変化】
[Dark Reading・The Hacker News・BleepingComputer 2026-08-04] デバイスコードフィッシングが2026年に1,500%増、ビッシングは倍増したとの統計が公表され、同日に商用PhaaS「Greatness」がデバイスコードフィッシング機能を追加しRingCentralを偽装してMicrosoft 365を狙っていることが報じられた

【概要】
OAuth 2.0のデバイス認可グラントを悪用する手口は、利用者がフィッシングサイトへ認証情報を入力しないためAiTM検知やパスワードリセット中心の対策が効きにくく、正規のMicrosoftドメインでコード入力が完結する。既報のStorm-2945（CaptiveCrunch）・DEBULL・Forg365と同一の攻撃面であり、本調査窓では統計面（Dark Reading）とツール面（Greatness）の双方で拡大が確認された。SOCとしては検知よりも先に条件付きアクセスポリシーでデバイスコードフローを制限する構成変更が有効である。

【推奨アクション】
・Entra IDの条件付きアクセスで認証フロー（デバイスコードフロー）を既定でブロックし、必要な業務のみ例外許可する
・サインインログでauthenticationProtocol=deviceCodeを抽出し、想定外の利用実態を洗い出す
・出張者・会議参加者向けに、正規のサインインでデバイスコード入力を求められることは通常ないと周知する
Splunk SPL: index=* sourcetype=azure:aad:signin authenticationProtocol=deviceCode | stats count values(appDisplayName) values(ipAddress) by userPrincipalName | sort - count
Splunk SPL: index=* sourcetype=azure:aad:signin authenticationProtocol=deviceCode | iplocation ipAddress | search NOT Country="Japan" | table _time userPrincipalName ipAddress Country appDisplayName
→ デバイスコードフローは会議室デバイス・IoT端末・CLIツールの正規サインインでも使われるため、まず正規利用の棚卸しを行ってから例外リストを確定する。国外IPからのデバイスコード認証は優先調査対象とする。

https://thehackernews.com/2026/08/greatness-phaas-adds-device-code.html

2. Open VSXマーケットプレイスの77拡張機能が開発環境情報を外部送信
観点: ゼロデイ関連
採用契機: δ / η
------------------------------------------------------------

優先度: 高
対象: Open VSX（VS Code系エディタの拡張機能マーケットプレイス）

【24時間以内の変化】
[BleepingComputer 2026-08-05] Open VSX上の77件の拡張機能が正規の開発ツールを装いながら、インストール先のシステムおよび開発環境に関する情報を外部送信していたことが判明したと報道

【概要】
Open VSXはVS Code系のオープンソースエディタ（VSCodium・Cursor・Windsurf等）が既定で参照する拡張機能マーケットプレイスであり、Microsoft公式マーケットプレイスより審査が緩い。開発端末は各種クラウド・リポジトリの認証情報を保持するため、環境情報の外部送信は後続の標的型攻撃の下準備となりうる。本日のChainDrop npmワーム（Section 2 APT本編）と合わせ、開発者環境そのものが継続的な攻撃対象になっている点をSOCとして認識すべきである。

【推奨アクション】

Splunk SPL: index=* sourcetype=edr:process process_name IN (code.exe,codium.exe,cursor.exe) | search command_line="*--install-extension*" | table _time host user command_line
Splunk SPL: index=* sourcetype=proxy user_agent="*VSCode*" | stats count dc(dest_host) as hosts by src_ip user | where hosts > 5
→ 拡張機能のインストール自体は日常的な開発行為であるため、アローリスト外の拡張IDに絞って抽出する。テレメトリ送信は正規拡張でも行われるため、送信先ドメインが拡張の提供元と一致するかで切り分ける。

3. XCSSET新亜種（v40）が侵害済みXcodeプロジェクト経由でmacOS開発者を標的化
観点: ゼロデイ関連
採用契機: δ / ε
------------------------------------------------------------

優先度: 高
対象: macOS / Xcode

【24時間以内の変化】
[BleepingComputer 2026-08-05] Unit 42が報告したXCSSETの新バージョン（v40）が、侵害されたGitリポジトリのXcodeプロジェクトファイルにダウンローダを注入して伝播していると報道

【概要】
XCSSETはXcodeプロジェクトファイルへダウンローダを注入し、開発者がプロジェクトをビルドした時点で感染し、さらに当該端末上の他のXcodeプロジェクトへ伝播する自己増殖型のmacOSマルウェアである。新亜種v40ではローダの定期再コンパイル、通信ごとの個別暗号鍵、関数・変数の難読化といった回避機能が強化され、Chromeハイジャッカーおよびtelegramトロイ化の2モジュールが追加された。加えてXProtect・MRT・TCC・Rapid Security Responseというシステム保護機構の無効化を積極的に行う。窃取対象は認証情報・ブラウザCookie・MetaMask暗号資産取引・通信内容で、ファイルレスのリバースシェルによるアクセスも確立する。IoCおよび帰属は記事内で提示されていない。

【推奨アクション】
・自組織のmacOS開発端末で、外部から取得したXcodeプロジェクトをビルドする運用の有無を確認する
・XProtect・TCC等のmacOS保護機構が無効化されていないかをMDMで点検する
・開発端末のEDRでファイルレス実行・シェル起動の検知ルールが有効か確認する

Splunk SPL: index=* sourcetype=edr:process os=macos parent_process_name IN (xcodebuild,Xcode) child_process_name IN (osascript,curl,bash) | table _time host user parent_process_name child_process_name command_line
→ xcodebuild配下からのosascript/curl/bash起動はビルドスクリプトの正規利用でも発生するため、プロジェクトのRun Script Phaseに当該コマンドが定義されているかをリポジトリ側で突合して切り分ける。

6. BMC（サーバ管理インタフェース）24,000台超の認証ハッシュ事前開示
観点: ゼロデイ関連
採用契機: γ / δ
------------------------------------------------------------

優先度: 中
対象: BMC / IPMI（サーバ管理インタフェース全般）

【24時間以内の変化】
[SecurityWeek 2026-08-04] インターネットから到達可能なサーバ管理インタフェース24,000台超が、ログイン成立前に認証ハッシュを開示している実態が報道された

【概要】
BMCはOSの外側でサーバの電源制御・仮想メディアマウント・リモートコンソールを行える管理面であり、掌握されればOS側のEDRやディスク暗号化を迂回した侵害が成立する。認証ハッシュの事前開示はオフラインでの総当たり解析に直結し、既定・共通パスワードを使い回している環境では実質的な認証バイパスとなる。個別ベンダーのCVEではなく設計・実装横断の露出であるため恒久的なパッチ提供が期待しにくく、ネットワーク到達性の遮断が主要な対策となる。

・管理インタフェースを専用の管理VLANへ隔離し、踏み台経由のアクセスのみ許可する
・既定パスワード・共通パスワードの使い回しを廃止する

→ IPMIのUDP/623はスキャンを受けやすいポートであり、外部ゾーンからの許可通信が1件でも存在する場合は構成の見直しを行う。管理セグメント内の正規監視システムからのポーリングは除外する。

9. マルウェアC2の約半数がDNSを迂回してIP直接通信（Unit 42調査）
観点: ゼロデイ関連
採用契機: γ / ε
------------------------------------------------------------

対象: ネットワーク監視全般

【概要】
DNSベースの脅威インテリジェンス（悪性ドメインのブロック・DNSシンクホール）のみに依存した検知では、マルウェアC2の約半数を取りこぼすことを示す定量データである。SOCの検知設計として、DNS解決を伴わない外向きセッションの可視化と、宛先IPレピュテーションによる評価を併用する必要性を裏付ける。

Splunk SPL: index=* sourcetype=firewall action=allowed direction=outbound | join type=left src_ip [search index=* sourcetype=dns | fields src_ip answer] | where isnull(answer) | stats count by src_ip dest_ip dest_port

10. CISA KEV 2026年7月追加26件・8割超が3日以内期限（BOD 26-04の運用実態）
観点: CVE関連
採用契機: α / ζ
------------------------------------------------------------

優先度: 低
対象: 脆弱性管理プロセス全般

【24時間以内の変化】
[Security NEXT 2026-08-04] CISAが2026年7月にKEVカタログへ26件を追加し、その8割超に3日以内の対応期限が設定されたと国内向けに報道

【概要】
BOD 26-04の運用下でFCEB期限が3日へ短縮されている実態を示すデータである。本日新規収載されたCVE-2026-18556・CVE-2026-34486・CVE-2026-9198の3件もdateAdded=2026-08-04に対し期限2026-08-07（3日）が設定されている。国内組織にFCEB期限の法的拘束力はないが、KEV収載から実際の攻撃観測までの猶予が短い前提で緊急パッチ適用プロセスを設計する必要がある。

【推奨アクション】
・KEV収載を検知した際の緊急パッチ適用プロセスが3日以内に完了できる体制かを点検する
・KEVカタログのJSONフィードを日次で自動取得し、自組織資産との突合を自動化する
Splunk SPL: index=* sourcetype=vulnmgmt:scan kev_listed=true | stats count by cve_id asset_count days_since_kev_added | where days_since_kev_added > 3
→ KEV収載CVEのうち自組織に該当資産が存在するものだけを抽出し、経過日数3日超を超過案件としてエスカレーションする。
