1. Zenity が Claude in Chrome／ChatGPT Atlas のゼロクリック乗っ取り手法を公開（記事時点で未修正）
観点: ゼロデイ関連
採用契機: ε / δ
------------------------------------------------------------

優先度: 高
対象: Claude in Chrome（Anthropic）／ChatGPT Atlas（OpenAI）

【24時間以内の変化】
[SecurityWeek 2026-08-06] AI セキュリティ企業 Zenity が、メール本文や X 投稿を介したゼロクリックの AI ブラウザ乗っ取り手法2件を公開。両社へは 2025年末〜2026年初頭に報告済みだが記事時点で未修正と報道（2026-08-05 公開・前回窓で未検知のため本日計上）

【概要】
攻撃者が細工したメールや X 投稿を AI ブラウザ拡張／エージェントに閲覧・処理させるだけで、利用者のクリックや権限確認プロンプトを経ずにアカウント乗っ取り・フィッシング・Amazon での不正購入などを引き起こせるとされる手法が公開された。研究者から Anthropic・OpenAI 両社へは 2025年末〜2026年初頭に報告済みだが、報道時点で未修正とされている。CVE 番号は付与されていない。実際の被害事例は本報道からは確認できていない（未確認であり、被害がないことの確認ではない）。Section 1〜3 のいずれにも帰属しないが、業務端末で AI ブラウザ拡張を利用している組織は即時に利用状況を把握すべき事案であるため SOC 推奨情報として採用した。

【推奨アクション】
・社内で Claude in Chrome または ChatGPT Atlas を業務利用している端末を棚卸しし、当面は利用制限または監視強化を検討する
・Anthropic／OpenAI の修正パッチ・アドバイザリ発行状況を継続監視する
・AI ブラウザ拡張プロセスからの異常な外部通信・購入系 API 呼び出しを EDR/プロキシの監視対象へ追加する
Splunk SPL: index=proxy user_agent="*Claude*" OR user_agent="*Atlas*" | stats count values(dest) as dests by user | where count > 200
→ 拡張の正常動作でも定期的な同期通信が発生するため、購入・決済・認証情報変更に関わるエンドポイントへの到達に絞って確認する。

【参照】
https://www.securityweek.com/zero-click-ai-browser-hacking-claude-and-chatgpt-atlas-hijacked-via-emails-x-posts/

2. Zbtlink 製ルーター20機種に工場出荷時から組み込まれたバックドア「ENDLESSDOORS」— C2 の IOC が公開
観点: ゼロデイ関連
採用契機: η / ε
------------------------------------------------------------

優先度: 高
対象: Zbtlink 製ルーター（20機種・21ファームウェアイメージ）

【24時間以内の変化】
[The Hacker News / VulnCheck 2026-08-06] VulnCheck が Zbtlink 製20ルーター機種・21ファームウェアイメージに工場出荷時から組み込まれたバックドア「ENDLESSDOORS」を公開。C2 ドメイン・IP・使用ポートの具体的 IOC を伴う

【概要】
VulnCheck は Zbtlink 製の20ルーター機種・21ファームウェアイメージに、工場出荷時から組み込まれたバックドア「ENDLESSDOORS」が存在すると公表した。無認証で LAN MAC アドレスを含む「hello」メッセージを外部へ送信し、C2 からのコマンドを受信して root 権限のリバースシェルを許可する。ビーコン間隔は35秒。2015年に公開された簡易 C2 ツール「rctl」をベースとした実装とされる。製造者 Zbtlink はアフターサービス保守用の機能と説明している。攻撃者の帰属・実運用での悪用事例はいずれも未確認だが、具体的な C2 IOC が公開されているため SOC として即日でアウトバウンド遮断・機器棚卸しが可能である。APT セクションでは軸P3/軸Q1と低スコアのため除外し、実運用価値の高い IOC を SOC 推奨情報として採録した。

【推奨アクション】
・自組織および委託先の拠点・小規模オフィスに Zbtlink 製ルーター（OEM 供給品を含む）が導入されていないか資産棚卸しを実施する
・境界ファイアウォールで C2 宛先（zbtctl.epplink[.]net / 47.100.190.96 / 47.107.224.89 / online-string[.]com / 45.32.81.152 / rbdg4nzqadui.wikaba[.]com / 43.248.136.125）および TCP 7000・7001 のアウトバウンドを遮断する
・過去90日分のプロキシ/ファイアウォールログを遡って上記宛先・ポートへの通信有無を確認する
Splunk SPL: index=firewall dest_port IN (7000,7001) | stats count dc(dest_ip) as dests by src_ip | where count > 10
Splunk SPL: index=firewall OR index=proxy dest_ip IN ("47.100.190.96","47.107.224.89","45.32.81.152","43.248.136.125") OR dest_domain IN ("zbtctl.epplink.net","online-string.com","rbdg4nzqadui.wikaba.com") | stats count by src_ip dest_ip dest_domain
→ 7000/7001 は正規アプリケーションでも使用されるため、宛先が上記 C2 と一致するか、または35秒前後の規則的間隔で継続しているかを併せて確認する。

【参照】
https://thehackernews.com/2026/08/chinese-made-zbtlink-routers-ship-with.html

3. CVE 番号を冠した GitHub リポジトリにプロンプトインジェクション用コーパスが混入 — AI 支援の脆弱性調査を標的とする手口を観測
観点: AI攻撃関連
採用契機: ε / γ
------------------------------------------------------------

優先度: 中
対象: AI 支援の脆弱性調査・脅威インテリジェンス収集ワークフロー全般

【24時間以内の変化】
[本パイプラインの追跡検証（一次観測） 2026-08-06] CVE-2026-64633（Veeam ONE）の PoC 有無を検証する過程で、同 CVE 番号を冠した GitHub リポジトリ（作成 2026-08-06T07:33:47Z・調査窓内）が実行可能コードを一切含まず、プロンプトインジェクション用テンプレート群であることを観測した

【概要】
CVE-2026-64633 の PoC 公開有無を一次確認する過程で、当該 CVE 番号を冠した GitHub リポジトリ（作成日時 2026-08-06T07:33:47Z・調査窓内）を発見したが、内容は payloads/ 配下の Markdown 文書群と manifest.json のみで実行可能コード（exploit.py / poc.py / main.py いずれも HTTP 404）を含まなかった。manifest.json は variant: treatment/control、is_control、pair_id、隠蔽度の指標といったフィールドを持ち、テンプレート種別は security_config / research_notice / cve_metadata / poc_comment / security_policy に分類されていた。この構造は、CVE 番号で検索する AI エージェントにコンテンツを読み込ませることを狙ったプロンプトインジェクションの A/B テスト用コーパスであることを強く示唆する（推測。運営主体・目的の公表はなく、第三者による報道・分析も本レポート作成時点で未確認）。安全のためペイロード本文は開いていない。本件は第三者ソースの報道ではなく本パイプライン自身の一次観測であり、Section 1〜3 のいずれにも帰属しないため SOC 推奨情報として記録する。AI を用いた脆弱性調査・脅威インテリジェンス自動化を運用する組織にとって、収集対象そのものが汚染されうるという運用上の示唆がある。

【推奨アクション】
・AI 支援の脆弱性調査ワークフローでは、CVE 番号で検索して得た GitHub リポジトリ等の内容を無検証で LLM のコンテキストへ投入しない運用ルールを設ける
・PoC の存在確認は実行可能コードの有無（ファイル実体）で判定し、リポジトリ名・README の記述のみを根拠にしない
・自動化された脅威インテリジェンス収集では、取得元ドメイン・リポジトリの作成日・スター数等のメタデータで信頼度を重み付けし、新規作成かつ実体のないリポジトリを低信頼として扱う
Splunk SPL: index=proxy dest_domain="github.com" OR dest_domain="raw.githubusercontent.com" | search uri_path="*CVE-*" | stats count values(uri_path) as paths by user src_ip
→ 正規の脆弱性調査でも CVE 番号を含む GitHub URL は頻繁に参照されるため、作成直後（数日以内）のリポジトリへのアクセスに絞って確認する。

【参照】
https://api.first.org/data/v1/epss?cve=CVE-2026-64633
https://www.veeam.com/kb4892

4. 米政府「GOLD EAGLE」— AI 駆動型の脆弱性調整クリアリングハウスが本格始動
観点: CVE関連
採用契機: ζ / δ
------------------------------------------------------------

優先度: 低
対象: 該当なし

【24時間以内の変化】
[ScanNetSecurity 2026-08-06] 「Scan PREMIUM Monthly Executive Summary 2026年7月度」で、米財務省・DHS/CISA・国防省が民間と連携し立ち上げた AI 駆動の脆弱性調整メカニズム「GOLD EAGLE」（大統領令14409に基づく）を日本語で解説する記事を掲載

【概要】
AI による脆弱性発見スピードの急激な加速に対応するため、米国が官民連携でスキャン・検証・優先順位付け・パッチ配布を調整する連邦クリアリングハウス「GOLD EAGLE」を稼働させた。施策自体の発足は 2026年6〜7月で調査窓外だが、国内向けの解説記事が本日窓内に掲載されたことを契機として採録する。AI が発見する脆弱性件数の急増に業界全体の対応力が追いつかない構造的課題への政策対応と位置づけられている。国内での直接適用はないが、同種の AI 駆動脆弱性管理の枠組みが今後国内の規制・ガイダンスへ波及する可能性がある（推測）。

【推奨アクション】
・中長期の動向として、自組織の脆弱性管理プロセスに AI 活用（検出・優先順位付け）を取り入れる際の参考事例として注視する
・米国拠点・米国政府取引のある組織は GOLD EAGLE 関連のガイダンス・要件変更を継続的にウォッチする

【参照】
https://scan.netsecurity.ne.jp/article/2026/08/06/55881.html
https://www.cybersecuritydive.com/news/vulnerability-clearinghouse-ai-white-house-launch-gold-eagle/825298/
